# 对话记忆与上下文控制架构决策文档

## 1. 背景与目标

在基于 eino 的 AI 应用（Chat / Agent）中，需要解决多轮对话场景下的上下文长度控制问题。核心目标：

- 控制每次调用外部 LLM API 时的 token 消耗量，避免超出上下文窗口。
- 保留关键结论，允许部分中间量缺失，不追求记忆的绝对准确与完整。
- 防止错误记忆静默传播导致幻觉加重。
- 保持架构简单，不在系统内部重复外部 LLM 已具备的能力。

## 2. 核心设计决策

### 决策一：记忆隔离与检索策略

- 所有记忆按 use_case 和 session 双重维度划分，非全量检索。
- 每次调用 LLM 时，将以下两部分内容放入上下文：
  - 根据当前 query 向量检索得到的三个历史回答摘要。
  - 上一轮回答的全文。
- 上一轮全文若过长，截取首尾各 512 token（或按字符数硬限制），确保不挤占系统提示与当前 query 的空间。

### 决策二：摘要方案 —— 保留关键原句

- 所有轮次的回答均由本地 SLM（Qwen3 家族，0.6B）提取摘要。
- 摘要范式：保留若干关键原句，重点覆盖前置条件和结论，中间推导过程允许部分丢失。
- 摘要与原文、元数据一并存入 Redis，并做持久化。
- 不在摘要中引入复杂逻辑（如二次检测、纠错验证、一致性检查），避免把外部 LLM 的职责内部化。

### 决策三：消息角色与置信度控制

- 历史摘要和上一轮全文统一放入 assistant 字段，保持消息结构原生。
- 在 system prompt 中添加一条规则，作为降低模型对历史记忆置信度的唯一手段：

```
你是一个助手。
回答前请先审视你之前输出的内容是否正确。
如果用户当前输入与历史结论矛盾，以用户当前输入为准。
```

- 不依赖系统内部二次检测来判断历史是否正确，判断对错的职责完全交给外部 LLM。

### 决策四：错误记忆的处理边界

| 场景 | 处理方式 | 系统是否介入 |
|------|----------|-------------|
| 用户主动纠正（如"你上一轮回答错误"） | LLM 原生能力处理，自动认错并修正 | 不介入 |
| 用户未纠正但历史记忆有误 | 依赖上述 system prompt 规则，LLM 在生成前自行审视 | 不介入 |

核心原则：内部只管"存"和"取"，不管"对不对"。不在系统侧重复外部 LLM 的判断能力。

## 3. 依赖与基础设施

| 组件 | 选型 | 用途 |
|------|------|------|
| 外部 LLM | OpenAI ChatModel（Chat 应用）/ agenticclaude.Model（Agent 应用） | 最终回答生成 |
| 本地 SLM | Qwen3 家族（chat / embedder / reranker），llama-server + docker 部署 | 摘要提取、向量化、重排序 |
| 向量数据库 | Qdrant | 混合检索历史摘要 |
| 缓存 | Redis | 存储元数据、原文、摘要，持久化 |
| 观测 | Langfuse | 服务观测，允许关闭 |
| 编排框架 | eino（v0.9.19） | Graph / Chain 编排，compose 层实现 |
| 提示词管理 | Viper + YAML + Jinja2 模板 | 热更新、多版本存储 |

go.mod 中无 task 相关官方实现。如需异步解耦摘要提取等耗时操作，推荐引入 Asynq（基于 Redis 的任务队列），但非当前阶段必需。

## 4. 上下文长度控制流程

```
用户输入 query
    │
    ├── 检索 Qdrant：取与 query 最相关的 3 个历史摘要
    │
    ├── 读取 Redis：取上一轮回答全文
    │       └── 若超过长度阈值，截取首尾各 512 token
    │
    ├── 组装 messages：
    │       system: 系统提示 + 审视规则
    │       assistant: 3 个历史摘要（按时间排序）
    │       assistant: 上一轮回答全文（标注为上一轮输出）
    │       user: 当前 query
    │
    └── 调用外部 LLM API → 返回回答
            │
            └── 本地 SLM 提取本次回答摘要 → 存入 Redis + Qdrant
```

## 5. 设计取舍说明

| 取舍 | 理由 |
|------|------|
| 摘要只保留关键原句，不追求完整 | token 有限，结论比中间量重要；缺失部分由 LLM 自行重新推导或向用户确认 |
| 不做系统侧二次检测 | 避免引入新错误源、增加延迟和维护成本；LLM 自身具备审视能力 |
| 历史记忆放 assistant 字段 | 保持消息结构原生；通过 prompt 规则降低置信度，而非改变角色 |
| 固定检索 top3 摘要 | 简单可控；若后续出现覆盖不足，可调整为动态计算数量 |
| 不引入全局渐进摘要 | 当前轮次规模下，top3 + 上一轮全文已足够；复杂度收益比低 |

## 6. 后续演进方向（非当前必需）

- 若对话轮次极多导致摘要膨胀，可引入全会话渐进式摘要。
- 若需解耦摘要提取与请求链路，可引入 Asynq 异步任务。
- 若 top3 固定数量不足，可根据剩余 token 窗口动态计算检索数量。
